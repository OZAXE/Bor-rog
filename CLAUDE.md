# Consignes du projet

Roguelite dans les enfers grecs, 3D isométrique inspirée de Hades, action en temps réel (Vite + Three.js, JavaScript sans TypeScript), publié sur GitHub Pages : https://ozaxe.github.io/Bor-rog/

Le propriétaire du dépôt n'est pas développeur de jeux : il juge sur des résultats testés et visibles. Explications en français, tutoiement, pas de tiret long.

## Conventions

- Commentaires du code en français.
- Pas d'éditeur graphique : tout est du code ou du texte (géométries, couleurs, sons générés en code).
- Performance mobile d'abord : InstancedMesh, MeshLambertMaterial, pas de shadow maps (ombre "disque"), pixel ratio plafonné (1,5 mobile / 2 PC), pas d'antialias sur mobile, une seule lumière ponctuelle. Objectif : 60 ips sur téléphone milieu de gamme.
- Contrôles : `event.code` (KeyW…) pour que ZQSD et WASD marchent sans réglage ; appareil détecté via `matchMedia('(pointer: coarse)')`, jamais le user-agent.
- `base: '/Bor-rog/'` dans `vite.config.js` doit rester égal au nom du dépôt (casse comprise), en dev, preview ET build.

## Direction artistique (validée : « option A », tout en code)

- Caméra isométrique orthographique, fixe, au sud-est (`src/camera/isoCamera.js`). Elle ne voit que le dessus et les faces sud/est des murs.
- Murs côté caméra abaissés selon `isLowWall` (`src/dungeon/tiles.js`) : un mur est bas s'il a du sol au nord, à l'ouest ou au nord-ouest.
- Décor fixe d'un étage = un seul maillage + un atlas de textures dessiné en canvas (`src/render/dungeonMesh.js`, `src/render/textures.js`). Lueur des flammes peinte dans les couleurs des sommets + halos additifs, pas de vraies lumières ni de bloom.
- Palette : ardoise bleu-vert, encre presque noire, flammes vert spectral, accents or. Personnages en cel shading (MeshToonMaterial) avec contour d'encre par coque inversée.

## Architecture (préparée pour un futur multijoueur)

- `src/state/` : état pur, sérialisable en JSON (y compris l'état du générateur aléatoire).
- `src/systems/`, `src/dungeon/` : simulation et génération pures, sans Three.js ni navigateur, exécutables dans Node. Les réglages des règles sont dans `src/systems/simConfig.js` ; `src/config.js` ne contient que l'affichage et les contrôles.
- Génération des étages : BSP (`src/dungeon/generate.js`), générateur dérivé de (graine, numéro d'étage). Les tests vérifient sur 300 graines que chaque étage est jouable.
- `src/render/` : lit l'état sans jamais le modifier. `src/ui/` : écrans HTML hors partie (Seuil) et stockage navigateur.
- `src/controls/` : produisent une "intention" `{ moveX, moveY, aimX, aimY, attack, dash, special }` exprimée dans le repère du MONDE (la conversion écran -> monde selon la caméra se fait côté client).
- Boucle à pas fixe 60 Hz (`src/core/fixedStep.js`) + interpolation d'affichage.

### Combat (étape 3)

- Règles et chiffres : `src/systems/simConfig.js` (durées en secondes, converties en pas entiers par `ticks()`).
- Héros : `src/systems/player.js` (attaque en arc, visée auto sans souris, esquive invulnérable, invulnérabilité après un coup). Ennemis : `src/systems/enemies.js` (machine à états idle / chase / windup / recover ; direction figée au début de la préparation pour que l'attaque soit lisible et esquivable). Flèches : `src/systems/projectiles.js`. Peuplement : `src/dungeon/populate.js` (générateur distinct de celui du plan).
- Escalier gardé (`stairsGuard` dans simulation.js) : pas de descente tant qu'un ennemi est debout dans la salle de l'escalier (ceux restés ailleurs ne comptent pas). Si des ennemis sont revenus dans la salle déjà purifiée, elle se scelle à nouveau (grilles, compteur) ; événement `stairsBlocked` (une fois par seconde) -> bandeau « Purifie la salle pour descendre ».
- Salles verrouillées (`src/systems/rooms.js`) : en entrant (au moins une case au-delà du seuil) dans une salle de combat occupée, des grilles (`TILE.GATE`, solides) ferment ses passages. Ne sont enfermés que les ennemis physiquement dans la salle à la fermeture (garantie anti-blocage, testée). Purifiée quand ils sont tous vaincus.
- Les ennemis contournent les obstacles : ligne droite si le passage est libre pour leur corps (`hasClearPath`), sinon carte des distances jusqu'au héros.
- Butin (`src/systems/loot.js`, étape 4) : oboles (attirées vers le héros) et potions lâchées par les ennemis, récompense au centre d'une salle purifiée, coffre dans chaque salle au trésor. Tirages via `state.rng`.
- Bienfaits (`src/systems/boons.js`) : l'état ne stocke que leur nombre (`player.boons`) ; `playerStats()` calcule les caractéristiques effectives. L'escalier ouvre l'écran de Charon (`src/systems/descent.js`, statut `choosing`, donjon en pause) : 1 bienfait parmi 3, soin et relance payants. Les choix passent par l'intention (`choice`, `shop`), jamais par une modification directe de l'état depuis l'interface.
- Difficulté (`src/systems/difficulty.js`, étape 5a) : par étage, PV et vitesse multipliés, +1 dégât tous les 4 étages, préparations raccourcies (plancher 60 %), élites (aura dorée) plus fréquentes. Les valeurs effectives sont calculées à la création de l'ennemi et rangées dans `e.stats` ; l'IA lit `e.stats`. Furie à partir de l'étage 3 (charge annoncée en ligne droite). Calibrage au bot : médiane de mort à l'étage 5 sans méta-progression.
- Zones et boss (`src/dungeon/zones.js`, étape 5b) : 3 zones de 3 étages (Tartare, Asphodèle, Élysée), ambiance par zone dans `src/render/zoneThemes.js`. Le 3e étage d'une zone est un étage de boss au plan fixe (`generateBossFloor` : départ -> arène scellée -> sanctuaire de l'escalier). Boss dans `src/systems/bosses.js` (config `SIM.bosses`), sans recul ni interruption ; chaque attaque annoncée. Les 3 boss sont faits : Cerbère (charge, souffle, morsure, phase 2 avec ombres), l'Hydre de Lerne (immobile au centre, têtes `hydraHead` tranchables qui repoussent sauf si on frappe le corps juste après = cautérisation ; phase 2 flaques de lave), Thanatos (faux circulaire, téléportation dans le dos, pluie d'âmes ; phase 2 doubles `thanatosDouble` qui se dissipent en un coup ; phase 3 plus rapide). Les parties de boss ont `part: true` (pas de butin, pas de recul). Zones au sol dangereuses : `src/systems/hazards.js` (`addHazard`, annonce puis frappe). Vaincre Thanatos met `status = 'victory'` (écran de victoire dans main.js). Calibrage avec un bot qui esquive 75 % des attaques : victoire Cerbère ~52 %, Hydre ~33 %, Thanatos ~10 %, combats de ~50-60 s.
- Roguelite (`src/meta/`, étape 6) : monnaie permanente, les Ombres (`state.shadows`, barème `SIM.shadows` : ennemi, élite, étage, boss), encaissées à la fin de la partie (mort, victoire ou abandon) par `recordRun`. Méta-progression façon Cyberpunk 2.0 (6c) : 4 attributs (Arès, Déméter, Hermès, Charon, `src/meta/tree.js`) du niveau 1 à 10, montés avec les Ombres (`ATTR_COSTS`) ; chaque niveau donne un bonus passif (`ATTR_EFFECT`) et 1 point de talent. Un arbre de talents par attribut : 4 paliers ouverts aux niveaux 1/4/7/10 de l'attribut, 2 chemins et un ultime ; un rang coûte 1, 2, 3 ou 4 points selon le palier (`TIER_COSTS`) : 36 points = un arbre complet et le bas d'un deuxième (builds). Talents repris gratuitement, niveaux acquis. `cleanMeta` rejoue les talents selon les règles : toute entrée (sauvegarde, code, simulation) donne un build valide. La partie reçoit `createGameState(seed, { meta: { attrs, talents } })` -> `state.player.meta` ; effets lus par `playerStats` (boons.js), player.js (critique, Exécution, Rage, Élan, Danse des lames, Défi de la Mort, Moisson), descent.js (Pacte, Marchandage, 4 bienfaits, relance gratuite, Racines), loot.js (Élixir, Œil), projectiles.js (renvoi). Un tirage n'a lieu que si le talent est possédé : sans amélioration, les parties ne changent pas. Profil v2 (`src/meta/profile.js`) ; les profils et codes v1 (ancien arbre) sont convertis en remboursant les Ombres. Seuil : `src/ui/threshold.js` (onglets, carte d'attribut, arbre avec liens SVG). Code d'export : `src/meta/transfer.js` (`BORROG1-<base64>-<somme>`).
- Calibrage 6c (bot à 75 % d'esquive, parties complètes, scripts botlib/variants/career2) : sans amélioration 0 % de victoires (mort médiane étage 4) ; tout au max avec un build offensif (Arès + Hermès) ~45 % ; build endurance (Déméter + bas d'Arès) ~80 % (le bot rate 25 % des esquives, la survie le favorise) ; à mi-parcours ~10-20 %. Carrière : 1re victoire vers la 14e partie, attributs au max après 21 à 25 parties.
- Classes (étape 7, `src/systems/classes.js`, chiffres dans `SIM.classes`) : Guerrier (héros de base `SIM.player`, épée en arc, 12 PV), Chasseresse (arc : flèche alliée qui traverse 1 ennemi, +1 par rang de Fendoir, 11 PV, plus rapide), Mystique (orbe lent qui explose en zone, rayon agrandi par Fendoir, 11 PV). `createGameState(seed, { meta, cls })` -> `state.player.cls` ; `playerStats` lit les réglages de la classe (`classRules`). Les tirs du héros sont des projectiles `friendly` résolus dans projectiles.js (`explode` pour l'orbe). Les 3 classes sont jouables dès le départ (demande du propriétaire : on les fait progresser, pas de déblocage ; `unlockBoss: null`, `classUnlocked` reste pour un éventuel retour) ; la classe se choisit aussi sur l'écran titre (`#start-classes`, recrée le héros avant la première descente). `state.bossesDefeated` -> `profile.stats.bosses` reste compté. Profil v4 (choix du propriétaire : « option B ») : chaque classe est un PERSONNAGE avec ses propres niveaux d'attributs et talents ; `attrs`/`talents` = personnage choisi (`cls`), `characters[classe] = { attrs, talents }` = les autres, rangés par `selectClass` (un personnage jamais monté n'est pas rangé) ; `characterOf`, `characterLevel` ; Ombres et statistiques communes ; `investedShadows` compte tous les personnages. Conversion v3 -> v4 : chaque personnage reçoit les anciens niveaux communs (rien n'est perdu) et son build rangé. Niveau de chaque personnage affiché sur les cartes (écran titre et Seuil). Le code d'export transporte `characters` (champ `b`). Calibrage (bot 75 %) : sans amélioration, les 3 classes meurent vers l'étage 4 ; le bot des tireurs garde ses distances, mais se rapproche des boss (Cerbère punit la distance). Capacités spéciales (7b, `SIM.classes[c].special`, `useSpecial` dans player.js) : intention `special` (une par appui, recharge `p.specialCooldown`) ; Tourbillon (coup circulaire, dégâts ×1,5, gros recul, invulnérable 0,3 s, 8 s), Volée (5 flèches en éventail, 7 s), Nova (zone, dégâts ×1,5, ralentit les ennemis hors boss : `e.slow`, ils ne pensent et ne bougent qu'un pas sur deux, 7 s). Contrôles : E / L / clic droit sur PC (jauge `#special-hud`), 3e bouton tactile `#btn-special` qui se remplit pendant la recharge. Calibrage avec capacités (bot qui se rapproche s'il ne touche plus rien depuis 5 s : sinon il restait bloqué à distance) : sans amélioration les 3 classes meurent vers l'étage 4-5 ; build endurance Guerrier ~92 %, Chasseresse ~83 %, Mystique ~81 % ; build force ~59 / 50 / 38 %. Arbres de classe (7c) : 7 talents par classe dans `TALENTS` (champ `cls`, `attr: null`), mêmes règles que les autres arbres mais paliers ouverts par la progression totale (`CLASS_TIER_LEVELS` = 0/9/18/27 niveaux gagnés), même réserve de 36 points ; `meta.cls` (cleanMeta) écarte les talents d'une autre classe. Guerrier : Parade (tirage seulement avec le talent), Riposte, Élan du cyclone, Grand cyclone, Rempart (+3 PV), Tempête (seconde frappe), Colère des Titans. Chasseresse : poison (`e.poison`, `tickPoison` dans player.js), Venin tenace, Carquois léger, Volée nourrie, Tir précis (au-delà de 5 m du point de départ de la flèche), Seconde salve, Instinct de chasse. Mystique : Orbe ample, Givre profond, Réaction en chaîne (tirage seulement avec le talent, 3 générations max), Nova vive, Orbes jumeaux, Bris de glace, Torrent d'âmes. Seuil : 5e onglet « arbre de classe ». Calibrage (arbre de classe complet + endurance/force) : Guerrier ~86 %, Chasseresse ~75 %, Mystique ~69 % ; sans amélioration, toutes meurent vers l'étage 4-5.
- Pause : bouton `#btn-pause` (PC et mobile, visible seulement en pleine partie) ou Échap / P ; menu `#pause-screen` (Reprendre, Abandonner la descente avec confirmation : les Ombres sont encaissées puis le Seuil s'ouvre). Changer d'onglet met aussi en pause. L'écran titre `#start-screen` ne sert plus qu'avant la première partie.
- Reprise d'une descente (8a, fait) : `src/state/savegame.js` (`serializeRun` / `parseRun` / `runSummary`) ; l'état complet (rng compris) est rangé dans le navigateur sous `bor-rog.partie` toutes les 3 s de jeu, à la pause, quand la page est cachée ou fermée. Effacé à la fin de la partie (`endOfRun`). Au chargement, l'écran titre propose « Reprendre la descente » ou « Nouvelle descente » (qui encaisse l'ancienne comme un abandon) ; un clic sur le fond ne lance rien. Une sauvegarde d'une autre `STATE_VERSION` est ignorée.
- Serveur (étape 8, `server/`, déployé sur Render via `render.yaml` : service web gratuit à Francfort, qui s'endort après 15 min sans visite) : Node, base Postgres chez Neon (gratuite, Francfort). Secret `DATABASE_URL` uniquement dans les variables d'environnement Render, jamais dans le dépôt. `/health` répond `{ ok, db }`. CORS limité à https://ozaxe.github.io (et localhost). Feuille de route 8 (faite) : 8a reprendre une descente en cours (local), 8b comptes + sauvegarde en ligne, 8c co-op à 2 dans la simulation, 8d réseau (salon avec code, simulation faisant autorité sur le serveur).
- Comptes en ligne (8b, fait) : serveur `server/app.js` (routes), `auth.js` (pseudo 3-20 caractères unique sans tenir compte de la casse, mot de passe ≥ 8 haché en scrypt salé, jeton aléatoire de 90 jours dont seule l'empreinte SHA-256 est stockée, pas d'e-mail donc pas de récupération), `pgStore.js` (tables accounts / sessions / profiles créées au démarrage) et `memoryStore.js` (mêmes règles, pour les tests). Le serveur relit chaque profil reçu avec `sanitizeProfile` (il importe `src/meta` : pas de rootDir dans render.yaml, `buildFilter` à la place). Limites : 5 essais de connexion ratés par minute et 5 créations de compte par heure par adresse. Chaque profil en ligne a une version `rev` : une écriture basée sur une version dépassée est refusée (409) avec la version du serveur. Client : `src/ui/account.js` (bouton d'état et panneau dans le Seuil, écran `#cloud-conflict`), règles pures dans `src/meta/sync.js` (`loginAction`, `refreshAction`). Le profil est toujours enregistré d'abord dans le navigateur (`bor-rog.compte` garde pseudo, jeton, rev, dirty), puis envoyé ; serveur injoignable = nouvel essai chaque minute. Un conflit (deux appareils ont avancé) n'interrompt jamais une partie : le choix est proposé au prochain moment calme. Sans compte, le jeu ne contacte jamais le serveur. Tests : `tests/server.test.js` (en mémoire ; `TEST_DATABASE_URL=postgres://... node --test tests/server.test.js` les rejoue contre un vrai Postgres), adresse du serveur dans `CONFIG.server.url`, `?server=http://localhost:10000` pour tester en local.
- Co-op à deux (8c, fait, simulation + partenaire bot) : `state.players` (tableau ; `state.player` n'existe plus), chaque joueur a son `id` (indice), sa classe, son build, sa bourse `p.gold` et son offre de Charon `p.offer`. `stepGame(state, intent)` en solo, `stepGame(state, [i0, i1])` en co-op. Les fonctions reçoivent le héros concerné : `updatePlayer(state, p, …)`, `hurtPlayer(state, p, …)`, `damageEnemy(…, p)`, `removeDeadEnemies(state, p)` (crédit : Rage, Tribut…), `healCost(p)`, `rerollCost(p)` ; attaques de zone : `hurtPlayersWhere`. Ennemis et boss visent `nearestPlayer` (héros actif le plus proche, `isActive` = ni à terre ni hors jeu) ; flaques et pluie d'âmes visent chaque héros à tour de rôle (`takeTurns`, sans tirage en solo). Projectiles alliés : `owner`. À terre (`p.down`, 15 s) : un allié à moins de 1,3 m pendant 2 s relève à 50 % des PV ; sinon `p.out` jusqu'à l'étage suivant (retour à 50 %) ; défaite quand plus personne n'est debout. En solo, la mort reste immédiate. Charon : chacun choisit, on descend quand tous ont choisi. Salle verrouillée : l'allié resté dehors est téléporté près de celui qui est entré. Butin au héros debout le plus proche (potion : seulement blessé). Difficulté (`SIM.coop`) : ennemis +100 % PV et +1 dégât, boss +130 % PV ; calibrage bot (guerrier + chasseresse) : sans amélioration mort vers l'étage 5, mi-parcours ~8 % de victoires (solo 0 %), tout au max ~71 % (solo 19-56 %). Le solo est garanti identique : 48 parties de bot rejouées au pas près avant/après la refonte. Mode de test `?coop=bot` : partenaire `src/controls/allyBot.js` (intention calculée depuis l'état, déterministe ; relève, combat, suit), vue `allyView` avec anneau vert, `#ally-hud`, `#down-info`. STATE_VERSION 9.
- Jeu en ligne à deux (8d, fait) : le serveur fait autorité. `server/rooms.js` (salons, sans réseau : testable avec de fausses connexions et une fausse horloge) fait tourner `stepGame` à 60 pas/s par partie (rattrapage plafonné à 5 pas) et envoie un instantané tous les 3 pas (20/s, compté par le salon `n`, car `tick` s'arrête chez Charon) ; `server/realtime.js` branche la bibliothèque `ws` sur `/play` (origine filtrée, compression permessage-deflate, 120 messages/s max, ping 20 s). Protocole et formats dans `src/net/protocol.js` (partagé) : intentions compactes `packIntent`, une file par joueur (12 max, une intention consommée par pas, la dernière répétée si la file est vide, `ack` renvoyé), choix de Charon par message `act` (appliqué une seule fois), décor envoyé une fois par étage (`fixed`), instantanés sans décor ni rng ni méta (`snapshotOf`), reconstitués côté navigateur par `stateFromSnapshot` (mêmes formes que la simulation, grilles posées depuis `lock`). Code de salon de 4 lettres (sans I, L, O), 2 joueurs, seul le créateur lance. Coupure : la partie continue, retour automatique par jeton (`rejoin`) ; départ volontaire : `p.left` (hors jeu définitif, ne choisit plus chez Charon). Fin de descente : le duo RESTE ensemble (`backToLobby` : même salon, `between`, absents retirés) ; chacun passe au Seuil (bandeau « En duo avec… », « Descendre » devient « Prêt », « Jouer à deux » devient « Quitter le duo ») et envoie `ready` avec son profil à jour (renvoyé s'il change après coup) ; la descente suivante part quand les deux sont prêts (`start` avec `run` + 1 ; même `run` = retour après coupure). Entre deux descentes, celui qui reste garde le salon ; seul, il repasse en solo. Salons fermés : lobby inactif 10 min, entre deux descentes 30 min, partie vide 2 min. Navigateur : `src/net/client.js` (réveille le serveur par /health, puis WebSocket ; visite /health toutes les 4 min pendant la partie), `src/net/netGame.js` (interpolation des autres avec 5 pas de retard ; prédiction de mon héros en rejouant `updatePlayer` sur une copie, réconciliation avec `ack`, écart lissé), `src/ui/lobby.js` (écran `#lobby`, boutons « Jouer à deux » à l'écran titre et au Seuil). Invitation : QR code (bibliothèque `qrcode-generator`, SVG sur fond clair) et bouton « Partager le lien » (`navigator.share`, sinon presse-papiers) ; le lien est `joinLink` (adresse du jeu + `?join=CODE`), lu au chargement par `codeFromLink` : le salon est rejoint directement et le paramètre retiré de l'adresse. Dans main.js : `myIndex`, `allyOf()`, `heroNow()`, `act()`, `netTick()`, pas de pause ni de sauvegarde de reprise en ligne. Débit mesuré ~5,6 Ko/s par joueur. Tests : `rooms-online`, `netgame` (latence simulée 60 ms), `realtime` (vrais WebSocket ; le CI installe `server/` avec `npm ci --prefix server`). `/health` renvoie `api: 2`.
- Le rendu ne modifie JAMAIS l'état : un test (`tests/purity.test.js`) scanne `src/render` pour l'interdire.
- Feuille de route validée : 5b = 3 zones de 3 étages avec boss et victoire (fait) ; 6 = roguelite (fait : Ombres, attributs et talents, sauvegarde navigateur + code d'export) ; ensuite classes (guerrier, chasseresse, mystique…), chacune avec son propre arbre de talents branché sur les mêmes attributs.
- La simulation signale ce qui s'est passé via `state.events` (vidé à chaque pas) ; le rendu en tire les effets (`src/render/effects.js`). Les effets peuvent utiliser Math.random : ils n'influencent jamais la partie.
- Budget mesuré : ~60 appels de dessin et ~11 000 triangles par image.

### Déterminisme (règle stricte)

- Tout le hasard de la simulation passe par `src/core/rng.js` (mulberry32), dont l'état vit dans l'état du jeu.
- Interdit dans la simulation : `Math.random`, `Date`, `performance.now`, Three.js, `window`/`document`. Le test `tests/purity.test.js` le vérifie.
- Même graine + mêmes intentions = même partie. Une graine peut être forcée avec `?seed=xxx` dans l'adresse.

## Vérifications avant de pousser

- `npm test` (node:test, sans dépendance) ; chaque nouveau test est validé en cassant volontairement le code pour vérifier qu'il échoue.
- `npm run build`
- Test visuel headless (vite preview + Playwright, Chromium dans /opt/pw-browsers) en viewport PC et mobile, sans erreur console. Le rendu y est logiciel (SwiftShader) : les ips mesurés ne sont pas représentatifs, et sous 12 ips le temps de jeu ralentit (rattrapage plafonné à 5 pas par image) : maintenir les touches plus longtemps dans les scripts. Google Fonts y échoue (certificat du proxy) : sans conséquence en ligne.

## Méthode de livraison (validée par le propriétaire du dépôt)

1. Travailler sur une branche, commits clairs (un par étape logique).
2. Ouvrir une Pull Request vers `main`.
3. Attendre que le contrôle « Contrôle » (`.github/workflows/ci.yml`) soit vert.
4. Fusionner la PR soi-même, puis vérifier que le workflow « Déploiement GitHub Pages » passe au vert.
5. Ne jamais fusionner une PR dont le contrôle est rouge.

La session cloud ne peut pas ouvrir *.github.io (proxy) : le site en ligne se vérifie via le statut du workflow de déploiement.
